# 简洁面评标准

每题一个 `modes/<mode>/sessions/<日期时间>-<mode>/` 文件夹。默认直接在本场 `solution.py` 写代码；用户指定外部文件时，结束后复制最终快照到本场文件夹，不覆盖原稿。

每次 wrap-up：记录完成状态，归档最终代码，写 `feedback.md`。题目保留在 `problem.md`，过程和帮助保留在 `session.md`。不要因只结束语音通话就自动结束面试。

## 六项评分

需求澄清、算法与正确性、代码实现、复杂度、测试与边界、沟通表达。每项 1–4 分，缺乏证据写 N/O：

- 1：存在关键缺口，尚不能完成。
- 2：部分完成，仍需明显引导或修正。
- 3：基本独立完成，存在小缺口。
- 4：独立、准确、稳健，能清楚解释。

每项附一句实际证据，不为凑分猜测。代码评分同时看最终质量和调试中需要的帮助；测试评分看候选人自己的测试设计，不能把面后自动测试算作候选人表现。不强行计算总分，也不映射公司录用结论。

## 帮助记录

- 澄清：解释题意，不算算法提示。
- 普通追问：要求复杂度、证明或例子。
- 定向排错：指出要检查的具体代码位置或状态，必须记录，即使候选人未主动请求提示。
- 提示 L1 / L2 / L3：引导问题 / 方向 / 具体步骤。

无主动提示请求不等于完全无帮助。区分独立提出的思路与经追问修正的部分。

## 面评篇幅

尽量一页：结论一句、六项评分表、帮助与验证说明、两项优点、最多三项改进动作。默认中文。长篇标准答案按需另存，不必每次附完整实现。

面后可做验证，但用户明确跳过运行时尊重其选择，标注“静态审阅，未运行”。未可靠记录暂停时不评价限时速度。
